# Trusted review runtime: owner setup and acceptance (issue #286)

Status: **code and workflows only. DISABLED, NOT ACTIVE, NOT live-verified.** Nothing here creates a key, sets a secret or variable, changes a ruleset, posts a review or check, or merges. Activation and the first live tests need your explicit approval after an independent exact-head review of the PR that adds this file.

Code: `scripts/trusted_review_runtime.py` (uses the merged `trusted_review_attestation.py` #283 and `trusted_review_evidence_collector.py` #285). Workflows: `.github/workflows/trusted-review.yml` (privileged, main only) and `.github/workflows/trusted-review-tests.yml` (secretless CI, required result `trusted-review-security-tests`). Tests: `scripts/tests/test_trusted_review_runtime.py`.

## What it does

- **Reviewer job** (environment `flowtally-trusted-reviewer`): for a PR into `develop`, collects evidence read-only, then approves only if every gate passes: Tier 0 docs-only paths; not draft, same repository; no unresolved or outdated threads; no pending reviewers; exact-head CI `backend`/`frontend` from `github-actions` with a provable base SHA; author, commit and `Claude-Session` separation; and a **separate review engine** result (below). It then builds the signed attestation, runs the real verifier over the review it is about to post, re-collects evidence to detect a moved head/base/file list, and only then posts one formal `APPROVE` with `commit_id` = exact head. A valid unexpired approval for the head is never re-posted.
- **Verifier job** (environment `flowtally-review-verifier`): verifies the latest formal approval from the pinned reviewer bot and publishes `trusted-review-verified` on the exact head from the verifier App only: `success` when valid, `failure` otherwise (missing, stale, expired, invalid, switch off, incomplete API evidence). Never neutral or skipped. The verdict comes from a fresh read taken right before publishing; if the head moved nothing is published, and any other change (new unresolved thread, CI failure, base moved, switch off) yields `failure`.
- **Independent engine.** The runtime does not rubber-stamp and does not call a model. It accepts the Codex GitHub App as the separate engine only through its pinned numeric bot id (`FLOWTALLY_CODEX_BOT_USER_ID`): the Codex summary comment (`codex-review-state:v1`) must be authored by that bot, name the exact head SHA, be `completed`, and report no unresolved findings. Comments by the shared `ter-ry` account, lookalike bots or older heads count for nothing. If Codex has not reviewed the exact head, the reviewer blocks. **Limitation:** this trusts Codex's own receipt; the runtime cannot re-derive Codex's judgement. No extra model or provider credential is needed or used. Phase 1 scope stays Tier 0 for this reason; migrations, finance, POS, security, workflows and `scripts/` are never approvable here.
- **Disabled by default.** Jobs do not run unless `FLOWTALLY_TRUSTED_REVIEW_ENABLED` is exactly `true`. Even then they dry-run (collect, assess, verify, print the plan without the signature) unless `FLOWTALLY_TRUSTED_REVIEW_LIVE_WRITES` is exactly `true`. Setting the switch to anything else stops all new approvals and checks at once, and the reviewer job stops running. The verifier job keeps a **revocation-only** path: if live writes were enabled and the verifier key is present, it publishes `failure` over any still-published `trusted-review-verified` success (it can never publish a success while the switch is off), so rollback closes the required-check gate within one schedule tick. If the switch was never enabled or live writes were never on, the job is inert. Consumers (the #270 controller) must also re-read the variable.
- **Triggers:** `workflow_dispatch` (optional PR number) and a 15-minute schedule, `refs/heads/main` only. There is no `pull_request`/`pull_request_target` trigger and no PR-head checkout. Runs are serialized by a concurrency group. The runtime also requires the workflow SHA to equal the current tip of `main`, the pinned repository id, and refuses to start if it can see the other role's secrets.

## Trust boundary: what the reviewer App does and does NOT prove (read before activation)

- The reviewer App **re-signs an upstream receipt**; it does not form its own judgement of the diff. The receipt is Codex's summary comment, authenticated only by Codex's pinned numeric bot id, the exact head SHA, `status: completed` and `has_unresolved_findings: false`. A "no findings" receipt means Codex raised nothing; it is an input, not proof of a substantive independent review.
- What the runtime adds on top, all fail-closed: Tier 0 docs-only paths (so the blast radius is documentation), author/commit/session separation, exact-head CI with a provable base, resolved threads, signed and expiring attestation bound to head/base/file digest, and a separate verifier identity that must agree.
- What it cannot establish: that Codex's receipt reflects a careful review, that the Codex App itself is uncompromised, or that Codex's comment format and bot id are stable. If GitHub or Codex changes the format, the reviewer blocks (never approves). Treat a Claude/CLAUDE-R1 or owner read of the first live docs PRs as a required acceptance step, not optional.
- Not covered by this PR: any path that is not Tier 0. Widening scope needs a separate owner decision and a stronger independent engine than a receipt.

## Owner setup (all manual; do none of this until you approve activation)

1. **Environments** `flowtally-trusted-reviewer` and `flowtally-review-verifier` (these are the names you already created; the workflow references them exactly, so no duplicate environments are needed): deployment branches `main` only, admin bypass off, no other secrets.
2. **Repository variables** (names shared with the #270 controller in PR #288; if a variable is missing the runtime fails loudly with `missing:<NAME>` instead of silently blocking): `FLOWTALLY_TRUSTED_REVIEW_ENABLED=false`, `FLOWTALLY_TRUSTED_REVIEW_LIVE_WRITES=false`, `FLOWTALLY_REPO_ID` (numeric id of `ter-ry/restaurant-helper`: `gh api repos/ter-ry/restaurant-helper --jq .id`), `REVIEWER_BOT_LOGIN=flowtally-independent-reviewer[bot]`, `REVIEWER_BOT_USER_ID` (`gh api users/flowtally-independent-reviewer%5Bbot%5D --jq .id`; the App id 5684233 is a different number), `FLOWTALLY_CODEX_BOT_USER_ID` (`gh api 'users/chatgpt-codex-connector%5Bbot%5D' --jq .id`; confirm it matches the actor on Codex's review comments), `FLOWTALLY_REVIEWER_APP_ID` (5684233), `VERIFIER_APP_ID` (settings page of `flowtally-review-verifier`), and `TRUSTED_COAUTHOR_EMAILS` (comma-separated, owner-vetted non-account co-author addresses; this repo's commits carry `Co-Authored-By: Claude ... <noreply@anthropic.com>`, so set `noreply@anthropic.com` if you accept that label as the coding assistant. If unset, such PRs are never approved: the collector refuses unresolved co-author identities).
3. **Signing key**, generated on a machine you control, never in Claude, CI or an issue:
   `openssl genpkey -algorithm ed25519 -out reviewer-signing.pem`
   Store the PEM only as environment secret `FLOWTALLY_REVIEWER_SIGNING_KEY` in `flowtally-trusted-reviewer`. Publish only the raw public key, base64, as variable `FLOWTALLY_REVIEWER_PUBLIC_KEY` (verifier environment):
   `openssl pkey -in reviewer-signing.pem -pubout -outform DER | tail -c 32 | base64`
   Delete the local PEM after storing it.
4. **App private keys:** reviewer App key only as `FLOWTALLY_REVIEWER_APP_PRIVATE_KEY` (reviewer environment); verifier App key only as `FLOWTALLY_VERIFIER_APP_PRIVATE_KEY` (verifier environment).
5. **App permissions (least privilege), both Apps installed on this one repository.** Reviewer: Pull requests read/write; Contents, Metadata, Checks, Statuses, Issues, Actions, Variables read; nothing else. Verifier: Checks read/write; Pull requests, Contents, Metadata, Statuses, Issues, Actions, Variables read; nothing else. The runtime mints a single-repository token with exactly these and aborts if GitHub grants a forbidden write (reviewer: any contents/checks/statuses/actions/administration/workflows/secrets/deployments/variables write; verifier: any write except checks).
6. **Ruleset on `develop`:** require `trusted-review-security-tests` and `trusted-review-verified`, restricting the `trusted-review-verified` source to the verifier App. Whether rulesets count an App approval or honor the source restriction is unproven and is part of acceptance below.

## Known limitations

- Nonce replay protection is bounded by head, base, file-digest binding and the 30-minute expiry; durable nonce consumption belongs to the Phase 2 actuator (#270).
- The schedule processes every open `develop` PR from this repository (fails closed above 500 open PRs); on a large backlog the 10-minute job timeout is the limit.
- The 15-minute schedule means a new approval can take up to 15 minutes unless dispatched.
- The 250-commit and 3000-file GitHub API caps make the collector report incomplete evidence, so such PRs are never approved.
- Real response shapes (user ids, `commit_id`, Codex comment format, App check-run `app.id`) are modeled on documented and recorded shapes, not live output; step 1 and 2 above confirm them.

## Diagnosing `installation_token_refused` (issue #292)

The runtime now prints `installation_token_refused:http_<status>:<category>`; the numeric status and a fixed category are the only provider-derived output (no JWT, token, headers or response text). Categories: `unauthorized_app_jwt` (401: wrong App id or private key), `installation_not_found` (404), `forbidden|unprocessable:installation_not_updated` (changed App permissions not yet approved on https://github.com/settings/installations), `:invalid_permissions`, `:repo_scope_mismatch`, `:unclassified`, `github_server_error`, `rate_limited`. On 403/422 the reason also carries `requested_undocumented_permission:variables`: GitHub's REST reference for `POST /app/installations/{id}/access_tokens` does not list a variables field (checked 2026-11-12), so if the status is 422 and the pending-approval check is clean, `variables` is the suspect. The request is intentionally unchanged (the kill-switch variable read and exact-repository scope stay; no broader token is minted) until the owner sees the real status.

**Fix for the 2026-11-12 dry-run 422 (`requested_undocumented_permission:variables`).** GitHub's `POST /app/installations/{id}/access_tokens` `permissions` field has no Variables key (neither `variables` nor `actions_variables`), although an installation token can read variables when the App holds Variables: read. The runtime therefore sends only `{"repositories": ["<repo>"]}` (single repository, inheriting the installed least-privilege App) and then verifies the granted permission map against an exact allowlist: any extra key, any higher level, or a missing required grant (including Variables read, accepted under `actions_variables` or `variables`) aborts with `installation_token_permissions_not_allowlisted:<unexpected|missing keys>`. The mandatory kill-switch variable read is unchanged. If the installed Apps carry any permission beyond the lists in section 5, the run fails closed and names the offending keys. Only a separately authorized dry run (live writes off) can confirm.

## Controlled live acceptance guard (#270)

Even with `FLOWTALLY_TRUSTED_REVIEW_ENABLED=true` and `FLOWTALLY_TRUSTED_REVIEW_LIVE_WRITES=true`, live writes (reviewer `APPROVE`, verifier check) are governed by a fail-closed policy in `scripts/trusted_review_runtime.py`. This replaces the earlier hardcoded `LIVE_ACCEPTANCE_PRS = (296,)` guard (#297), which was only for the controlled PR #296 acceptance test.

1. **Run level (`live_target_allowed`).** A manual `workflow_dispatch` with an explicit `pr_number` may write for that PR. Scheduled runs and blank-input reconcile-all runs write **only** if the separate owner variable `FLOWTALLY_TRUSTED_REVIEW_UNATTENDED` is exactly `true` (new, default unset = dry-run; wired into both jobs in `.github/workflows/trusted-review.yml`). Other events never write. Revocation-only (failure) behavior is unchanged.
2. **Per-PR eligibility (`live_eligibility`), applied on fresh evidence immediately before any write, on top of the existing `assess` gates:** base `develop`; open; not a draft (unknown counts as draft); head in this repository (forks and unknown heads refused); 1 to 25 changed files; every file (including rename sources) Tier 0 (`docs/**/*.md`, nothing under `.github/`, `scripts/`, `backend/`, `src/`, agent instruction files, migrations or settings). Reviewer `APPROVE` and verifier `success` need eligibility; a verifier `failure` verdict only withdraws trust and is always publishable when the run-level gate passes. An ineligible PR yields `dry_run` with the reasons.
3. **Write cap.** At most 3 live writes per run (`MAX_LIVE_WRITES_PER_RUN`), shared across all PRs; further writes are refused and reported as unconfirmed.

Unchanged: Codex exact-head receipt, signed attestation, preflight verification, head/base re-fetch, kill switch and isolation of the two roles. Widening this policy is a reviewed code change. Nothing here turns a switch on; setting `FLOWTALLY_TRUSTED_REVIEW_UNATTENDED=true` is an owner action that should follow a successful manual acceptance. To go back to dry-run, unset it (or set live writes false).
